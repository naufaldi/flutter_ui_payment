## Customization

### D106 — Soft host preset in the example (4 November 2026)

The example app has a third named host preset, **Soft** (`DemoBrand.soft` in `example/lib/themes.dart`), beside Hairline (the default) and Contrast/Lumen. Soft is a token change only: a tinted page (`#F1F2F6` light, `#0E0F13` dark) with white or lifted panels, an indigo accent (`#3D4AC4` / `#AEB7FF`), D101 radius roles of 8 (tags), 12 (controls), 16 (boxes) and 20 (sheets), white field fills through `PaymentFieldTheme` (D102) and a lighter `amountWeight` (w500). The inset panel (`SoftInsetPanel`, `example/lib/compositions/`) is host styling: a surface panel with a 1 dp outline and the sheet corners, inset `related` from the page, with no shadow, scale or motion. `lib/soft_merchant_demo.dart` runs the Merchant overview block in it; the gallery's brand setting also offers Soft.

**Why:** issue #151 asked for a showcase theme that reads clearly unlike Hairline and Contrast, so a host can see that the same widgets carry a softer product look. PR #152 planned this direction in `docs/design-research.md` §9; this decision implements the part that is useful now and records it there as current.

**Contrast:** on the tinted light page, body text is 14.3:1, secondary text 5.6:1, the accent 6.3:1, the control edge 3.5:1 and the fixed status tones at least 5.6:1; in dark mode every pair is higher. Disabled labels stay above 2:1 on the muted fill, as for Hairline.

**Unchanged:** no package API, variant, brand API, chart series palette API or new dependency. Charts keep D39 ramps and dash. Kit rules override generic web guidance: 48 dp targets (B5) rather than 44 px, no press scale on full-width buttons, and no optimistic payment states. Hairline stays the default for docs captures; Soft has its own Merchant overview captures.

**Not chosen:** a decorative layer (confetti, colored shapes), a desktop dashboard shell and a kit-level panel widget. A panel is layout the host owns. Cost: a third preset to keep in contrast checks. Proof: one widget story at 320 dp and 200% text (`example/test/merchant_overview_test.dart`) and Android phone captures in light and dark.

### D104 — Connected host checkout example (4 November 2026)

`HostCheckoutJourney` is copyable application source in `example/lib/compositions/`, not a package export. It reuses the invoice and recovery compositions with a pinned priority action and the product Button/Field theme. One host-provided attempt identity survives submission uncertainty and status checks; host snapshots reconcile through the existing model. Failed refresh retains last-known state, and a failed receipt load can retry without resubmitting. `order.reference` identifies the mounted session, while the submitted order fixes the displayed amount; a generation check prevents callbacks from a previous session populating a new one. The host must not change that reference merely to refresh a quote or abandon an unresolved payment.

**Why:** the D98 checkout and recovery specimens were independently usable but did not show a connected host journey without `DemoCoordinator`. Connecting them demonstrates the adoption model without adding another kit runtime, theme API, dependency or platform effect. `InvoiceCheckout.inlinePayAction` is example-only structure: false lets the host move that same action to its screen footer.

**Limits and ownership:** this sample requires a current quote priced for the selected method and checks it again at the submit event. The host still persists the attempt before sending, revalidates financial terms and authorization, parses authoritative responses, validates complete receipt data, and supplies routing, sharing and clipboard callbacks. Local presentation state is not process-death persistence. The synthetic wallet fixture requires no challenge; real challenge cancellation must be handled by the host before submission. The scope is a mounted checkout-to-receipt story, not block distribution or a new backend. Approved by the owner's connected-flow request, 4 November 2026.

### D103 — Toast follows the caller's scoped themes (3 November 2026)

`showPaymentToast` now captures the inherited themes between its `context` and the `ScaffoldMessenger` once, when the toast shows, and wraps the pill content in them. This is the same `InheritedTheme.capture` pattern the phone sheet, side sheet (D100 batch 1) and confirm dialog use. A toast raised inside a feature-scoped `Theme` paints that scope's `PaymentTheme`: ink fill (`textPrimary`), control corners, message and tone-icon color (`surface`) and action foreground.

**Why:** the app's root messenger renders every toast outside any feature scope. Before this, the toast was the only kit overlay that ignored the caller's themes, so a feature with its own look raised an app-styled toast. Capture matches the other overlays and needs no new API.

**Snapshot and live behaviour:** scoped themes are captured once. If the scope changes while the toast shows, it keeps the captured look until it closes or is replaced. App themes above the messenger are not captured and remain live only where a captured theme does not shadow them. A captured Material Theme freezes its entire ThemeData, including values copied from the app. With no scope between caller and messenger, rendering is identical to before.

**Material 2 close icon:** a captured `Theme` replaces SnackBar's M2 inverted theme inside the pill. The close icon keeps the SDK's M2 default under D80 (the uninverted `onSurface`), so the kit resolves that one fallback explicitly: from the caller's scope when a `Theme` was captured, otherwise from the inverted theme as before. Material 3 is unchanged.

**Unchanged:** the D77 replacement queue, D95 footer lift, pending, controller update/dismiss, timers, reduced motion, focus and semantics. No toast style API; a feature restyles its toasts by scoping `PaymentTheme`, as for every other family. This amends the source context of the D22 ink tokens and D80 and supersedes nothing.

**Cost and limits:** one ancestor walk and one capture per show; no listener, timer or frame work. A host that wants an open toast to follow a scope change shows a new toast. Proof: one widget story with a root messenger and a scoped feature theme (`test/toast_theme_scope_test.dart`), plus the existing toast suites.

### D102 — Field-family theme (3 November 2026)

`PaymentFieldTheme` is a `ThemeExtension` with four nullable properties: `fillColor`, `borderColor` (the enabled resting outline), `borderRadius` and `textStyle` (typography merged over `PaymentType.input` for the entered value and placeholder). Every field box reads it through one internal resolver: the shared `paymentFieldDecoration` (text, search, text area, date, currency), the select/date-range/compact-search trigger (corners of the tap highlight and the value text) and the text field's value and placeholder style. Promo code and identity form compose those fields, so they follow. Option lists, panels, sheets, chips, selection controls, buttons and cards are untouched; `PaymentDateRangePicker.button` is an icon button and is unaffected.

**Why:** inputs shared the control radius with other controls (D101 can only move them together) and had no fill or input typography surface. Products asking for soft filled fields or a heavier input face had no supported path without restyling buttons too.

**Why theme-only:** forms want consistent fields; a per-field `style` invites drift and multiplies the state surface. A scoped `Theme` covers a feature or a single exception. No separate style class was added without a story needing one; a later instance surface would need a demonstrated gap.

**State contract:** the kit keeps focus (2 dp accent), error (danger) and disabled outlines, disabled text colors and read-only behaviour. A custom fill becomes `surfaceMuted` while disabled; with no custom fill the box stays unfilled and a host `InputDecorationTheme` fill still applies, as before. Labels, helper and error text keep their roles. Padding and sizes stay kit-owned; a custom font size or line height changes the text line, so the box follows like it does for system text size, never below Material's 48 dp minimum. The currency field keeps the amount role for the entered amount and follows the themed input line height with the default input line as its minimum, so smaller input typography cannot clip amount digits.

**Interpolation:** typography is normalized before merge or `TextStyle.lerp` (shared with D100 through an internal, unexported helper), so ignored paint or `inherit: false` cannot throw or leak. Concrete pairs interpolate; a value set on one side only switches at the midpoint, keeping null as "kit default" rather than fading from transparent or square.

**Cost and limits:** hosts verify the contrast of a custom fill against input text, placeholder and outline in light and dark. `copyWith` cannot clear a value back to null; build a new theme. A themed border color can make the resting outline weak; the host owns that pair. No new dependency, effect, timer, listener or frame work; resolution is one extension lookup per build. At this batch, other families and adoption proof were pending; the completed review and local verification are recorded in the D98 family disposition above.

### D101 — Theme radius roles (3 November 2026)

`PaymentTheme` gains three optional role radii: `tagRadius`, `controlRadius` and `sheetRadius`. `radius` remains the box role and the base. An unset role keeps its current multiple of it (tag 0.5, control 0.75, sheet 1.5), so existing themes render identically and ordinary constructor/call-site usage stays compatible. Downstream subclasses overriding `PaymentTheme.copyWith` must accept the new named parameters. `tagBorderRadius`, `controlBorderRadius`, `sheetBorderRadius` and `PaymentRadius.resolve` read the role, and every kit consumer already reads those getters, so badges, buttons, fields, notices, menus, sheets and dialogs follow without per-widget style fields. A host can now ship square boxes, pill tags and rounder sheets while keeping controls where they were.

**Why:** a single base with fixed multiples ties every corner together; a product with square cards and pill badges had no supported path. Role fields on the existing theme reuse the existing resolution and need no new class.

**State and interpolation:** unlike D100's style layer, the theme can resolve its own defaults. When either side of `lerp` sets a role, it interpolates the radii each side actually draws, so an unset side animates from its derived value, never from zero or a midpoint jump. When neither side sets it, the role stays null and keeps following the animating base. Values are asserted finite and non-negative; zero is a valid square corner.

**Cost and limits:** `copyWith` follows the class convention, where null retains, so it cannot clear a set role back to derived; build a new theme for that. No reset flag is added without a story. A lerped theme can carry a concrete role at its ends; it draws the same radius as its endpoint. `PaymentTheme` has no value equality today, and none is added. Field-family theming remained a pending D98 batch at the time; it landed as D102.

### D100 — Button customization pilot (3 November 2026)

Theme interpolation normalizes typography before calling Flutter's text interpolation, so ignored paint and `inherit` cannot cause a transition error. Concrete override pairs interpolate; fields missing at either endpoint switch at the midpoint, preserving null as semantic inheritance rather than transparent colors or zero radius. The style layer cannot resolve the underlying semantic defaults itself, so these one-sided overrides deliberately do not animate through invented defaults.

`PaymentButton.style` takes `PaymentButtonStyle`: enabled background/foreground, secondary border color, corner radius and heading typography. `PaymentButtonTheme` is a `ThemeExtension` with shared and per-variant styles. Resolution is token defaults for selected variant/size, shared family style, variant style, then instance non-null fields; text typography merges. Scopes preserve other extensions and derive from the parent when desired. This enables pill buttons without rounding inputs. No content slot is added without a story requiring one.

Flutter `ButtonStyle` is not forwarded because its sizing, state and motion controls exceed this contract. Padding, heights, density, hit target, icon size, alignment, state-specific colors, focus color and motion stay kit-owned. Text colors/paint/background/shadows/decoration and `inherit` are ignored; foreground controls label, icon and spinner. Disabled colors remain tokens, the neutral focus ring follows the resolved radius, and pressed/hover layers derive from foreground. A custom quiet fill uses the disabled surface when disabled. Disabled+busy now uses the disabled spinner color rather than the enabled foreground, a narrow correction to current-state consistency. Other default rendering and source compatibility are preserved.

Adoption clarification: offering a theme extension, a style type and an instance parameter does not make repeating the same inline style everywhere the intended use. Docs and examples lead with theme defaults and style-free call sites, use a named host preset (taking `BuildContext` so tokens follow light/dark) for an intentionally repeated subset, and show an inline override last as a one-off. Inline copies drift and bypass theme changes; presets stay host code so the kit API remains bounded. This clarifies D98/D100 guidance without a new decision or runtime change.

Compliance note (batch 1 of the D98 migration): a button's instance `style` now survives the kit slots that re-create it at hug width (button group, banner actions, view footer, page module actions, action bar); a group's collapse-to-menu still renders menu rows, which do not take button styles. `showPaymentSideSheet`, and so `showPaymentFocusView` on wide windows, now captures the caller's inherited themes like the phone sheet and confirm dialog, so a feature-scoped `PaymentTheme` or `PaymentButtonTheme` also styles the panel surface and its buttons. Runtime fixes only; no new decision or public API, and other families were pending at that batch; see the completed D98 family disposition above.

Hosts verify custom contrast and content. No new dependency, platform effect, timer or animation is introduced. Six focused stories cover theme transitions, default equivalence, scoped family styling, instance precedence, state safety and large-text targets; existing Button regression tests remain unchanged. Other families and host checkout compositions were pending at the pilot; the D98 family disposition above records their completion. Cost: a deliberately bounded style API, with extra properties requiring a demonstrated story rather than unrestricted pass-through.

### D98 — package foundation customization (3 November 2026)

**Owner-approved direction; family review and host adoption implemented (D100–D103, [family disposition](#d98-family-disposition)); combined tests, Android light/dark captures and independent review passed locally on 3 Nov 2026 (not published or deployed).** The foundation remains a Flutter package whose components can be restyled and recomposed in host projects. The contract and phased acceptance criteria are in [PRD §2, Customization and composition](prd-foundation-components.md#customization-and-composition-contract-d98).

- **Appearance:** shared semantic tokens, scoped component-family themes where needed, existing variant/size choices, then typed per-instance styles. Resolve token defaults for the selected variant/size, then the nearest family theme, then non-null instance overrides. Keep supported properties and state resolution explicit. Prefer Flutter style types when they fit; do not forward every geometry property without enforcing kit rules.
- **Structure:** use widget children and named slots; add builders only for content requiring component-owned data/state. Product layouts and future copyable blocks remain host-owned compositions accepting data and callbacks, without `DemoCoordinator` dependencies.
- **Boundaries:** B2 still governs kit-owned defaults; documented host theme/style values are permitted customization inputs. The 48 dp target, focus/semantics, 200% text at 320 dp, reduced motion, repeated-action protection and payment invariants remain. Hosts retain content/colour-pair responsibilities and all business decisions and platform effects; dependencies remain Flutter-only.
- **Migration:** review all exported visual families, change only demonstrated gaps, and preserve compatibility/default rendering. Start with Button, expand by related family, and prove two different checkout compositions. Models and formatters do not receive artificial style APIs. Existing state ownership and D34 deprecation rules remain.

**Why:** theme changes alone cannot express local appearance and structural changes. Universal style/builders on every component would add API complexity and could bypass tested behaviour. **Cost:** each changed family needs a documented resolution contract, state-safe rendering and focused verification. This records direction rather than claiming new API availability; it authorizes no merge or deployment.

## Scope

- **Bounded inventory.** "All components" was interpreted as: interaction (action rows, menu, confirm dialog, snack bar, disclosure, loading/empty/error), navigation (sidebar, drawer shell), sheets/drawers, video, promotions, and payment additions (action bar, merchant header, step indicator, balance, promo code, transaction history and detail). Not a general design system: Material widgets that already work are used directly rather than wrapped.
- **Out of scope, still.** Real wallets, PIN entry, card storage, ledgers, ad SDKs, real campaigns, tracking. These appear as a disabled "Saved cards" item in the gallery to show the disabled-with-reason state.
- **One package.** New modules live in the same package (`lib/src/interaction`, `navigation`, `overlay`, `media`, `promo`, `payment`). Splitting would only pay off once a consumer needs part of it without the rest.

## API shape

- **Composition over configuration.** `PaymentSheet(header:, body:, footer:)` takes widgets, not a config object; `PaymentSection` gained an optional `trailing:` action instead of a new card type.
- **Controlled where the host owns state, uncontrolled where it doesn't.** `TransactionHistory` (query, filter, records) and navigation selection are fully controlled. `ExpandableSection` supports both modes.
- **Host verdicts, not UI math.** `BalanceCard` takes `BalanceState`; `PromoCodeInput` takes `PromoCodeStatus`; a discount reaches the total only as a new host quote. This keeps the payment invariants from v0.1 intact.
- **Media through an adapter.** `PaymentVideoController` is an abstract `ValueNotifier`. The package stays free of native plugins; the example's 100-line adapter uses the official `video_player` 2.11.1, already cached locally and compatible with Flutter 3.44 and Android API 24.
- **Strings in an extension.** New strings are `KitStrings` on `PaymentLocalizations`, so hosts keep one delegate.

## Accessibility decisions

- Drawer: opening moves focus into it; scrim, Back and Escape close it; focus returns to the menu button; closed items are not in the tree.
- Disabled navigation and action rows stay visible with a reason; they are not focusable.
- Destructive confirmations put initial focus on the safe choice.
- Sheets separate **Close** (UI only) from **cancel payment** (host request behind confirmation, result still pending until the host confirms).
- Video: every control has a label, the seek slider speaks "0:04 of 0:08", and loading, buffering and finished states are announced.

## Performance

The PRD budget is p95 build and raster each under 16.7 ms on a recorded 60 Hz target after a 30 s warm-up. The harness now measures a 30 s window (it measured 20 s before). Android 11 arm64 emulator, profile mode, Impeller on OpenGL ES, X02 checkout at 200% text, fling both ways plus method switch:

| Run | Workload | Build p95 | Raster p50 | Raster p95 |
| --- | --- | --- | --- | --- |
| Before this pass (20 s window) | Checkout 200% | 2.16 ms | 14.92 ms | 19.49 ms |
| Attempt 1 | Checkout 200% | 1.85 ms | 16.63 ms | 31.13 ms |
| Attempt 1 | Same at 100% text (diagnostic) | 1.96 ms | 16.26 ms | 31.83 ms |
| Attempt 2 | Checkout 200% | 2.02 ms | 16.12 ms | 20.41 ms |

Build time is within budget. The plain Material list also misses the raster budget in the same session. The similar control results and session variance suggest that the emulator's presentation path contributes substantially. They do not isolate every kit rendering cost or prove that the kit cannot be improved. The raster budget is **not met in this environment**. A comparable measurement on another suitable runtime or device would help isolate the cause; physical hardware is not a new mandatory delivery gate.

Artifact limitation discovered during parent review: the screenshot driver overwrote `build/perf/summary.json` with screenshot report data after Attempt 2. Those image bytes were preserved outside the profile folder; Attempt 1's raw metrics remain in `build/perf/checkout_attempt1.json`. Attempt 2's numbers above are the implementation run's recorded results, but its raw summary was not retained. The driver now writes performance output only when the report contains checkout metrics, so later screenshot runs cannot overwrite it. Future profile runs create `summary.json` again. No additional benchmark was run just to replace this artifact.

## Parent review fixes

- A loading video could become ready after the app entered the background and trigger opt-in autoplay. A focused regression reproduced it. Playback now tracks foreground state and consumes autoplay on backgrounding, so returning always requires a tap.
- Older gallery examples contained empty callbacks and clipboard callbacks that reported success without copying. They now show explicit synthetic-host feedback, simulate authorization, preview allowlisted receipt text, and use the real clipboard API with failure handling. The full business flow remains in the Demo tab; gallery feedback does not claim a payment or KYC submission.
- The new component journey was run on iPhone 16 / iOS 18.1. Native video advanced to 4.5 seconds, paused on tab change, and the generated screenshots were inspected.

The code changes that removed per-frame work in checkout (no opacity layer during re-quote, no rounded clip per method tile) are justified by inspection. On this emulator their effect is below the noise.

## Charts and KYC capture (31 Oct 2026)

Charts here are customer-facing spending summaries. PRD §4 excludes operational dashboards; this work does not add one. PRD.md stays unchanged.

- Chart values are Money and each chart uses one currency. Only settled values enter spoken lowest/highest/latest summaries. Pending is outlined/dashed, unknown is hatched/dotted, and missing leaves a gap. Unknown must never look like pending.
- Host verdicts, not UI math: a ChartModule headline and delta come from the host. The kit never computes a displayed total. Meter widths use amounts, while legends show amounts, never percentages.
- ChartState mirrors PromoSlot states. Hosts choose loading > error > empty > ready. Plot height stays constant across states; meter height is intrinsic.
- Meter categories use an accent-to-surface ramp with at most five entries, constrained to 3:1 surface contrast. Status tones are not categories. Hosts group extra categories into Other.
- Compact money is only for axes: Indonesian rb/jt/M/T with NBSP; English K/M/B/T. Integer rounding promotes a carried suffix and never changes payment confirmation formatting.
- Line/bar pointer inspection is supplemental and has no keyboard inspection target. Generated summaries expose the same amounts without pointer use. No multi-series chart support.
- Capture source choice precedes host permission. The kit opens no camera, gallery or file picker and performs no OCR, liveness, face matching or photo scoring. The host owns photos, uploads and verdicts. Uploaded is not verified.
- Camera previews use a theme-independent black54 scrim and white outline for visibility over arbitrary content. Illustration surfaces use theme tokens. Overlays ignore pointer input.
- Demo photos use PictureRecorder, a CONTOH / SPECIMEN watermark and a drawn masked NIK. Photo bytes live only in the capture screen. SyntheticIdCard uses PrivacyMask for its NIK row.
- The foundation specimen adds compact money; the amount, info-row and status-badge alt text changes travel with the refreshed capture.

- **D59/D62 implementation note: one footer rule for the action bar (#79).** The P7c sweep showed the iPad checkout's "Tinjau pembayaran" full width while every other pinned footer put its hug buttons at the end edge. `ViewFooter`'s test moved into an internal `footerStacks(context, width)` in `view_frame.dart` (stack when the footer is narrower than 600 dp or text is large), and `ViewFooter` calls it unchanged. The width is the footer's available content width after its padding, not the window: with the default 16 dp gutters a 600–631 dp window still stacks and hugging starts at a 632 dp window, the same as `ViewFooter`. `PaymentActionBar` asks it only when it has no `total`, from a `LayoutBuilder` inside `PinnedFooter`, so the width it tests is the 640 dp column, not the window. Stacked, the action is laid out as before. Wide, it sits at `AlignmentDirectional.centerEnd`: a `PaymentButton` through `hugButton` (as `ViewFooter` does, keeping its key and the 112 dp minimum), any other widget at its intrinsic width with the same 112 dp minimum. The `Align` takes `heightFactor: 1`: a `Scaffold` offers its bottom bar the full height, so without it the bar filled the window and the body above got none; the example's wide-checkout test caught it, and the kit test now checks the bar's 72 dp height. - **D53/D62 implementation note: the footer's column follows the content's (#84).** On iPad landscape the example's checkout put the order context beside the form in a column up to 1040 dp while the pinned `PaymentActionBar` kept the 640 dp column, so the bar's action stopped short of the content's end edge. Kit views already did this: `ViewFrame` passes its `maxContentWidth` to `PinnedFooter`, and `PaymentFullPageView` and `PaymentDetailPage` pass 1040 when they show two columns. `PaymentActionBar` sits in the host's `Scaffold.bottomNavigationBar`, outside any view, so it gains `maxContentWidth` (default 640, the same value as the internal `kContentMaxWidth`, so existing bars don't change) and passes it to its `PinnedFooter`. In the example one function, `contentCap(width, step)` in `flow_screen.dart`, gives 1040 for checkout from 840 dp of content and 640 otherwise, and the list's inset and `_CheckoutBar` both read it. Its input was wrong too: `listInset` measured the window with `MediaQuery`, but from an 840 dp window the example shows a side rail, so the list column came out narrower than its cap (at a 1024 dp window, about 559 dp beside the iPad's 80 dp rail and 1 dp divider, and 510.5 dp in the widget tests, whose test font makes the rail about 130 dp), and the "872 dp" two-column threshold in #84 was window arithmetic. The flow screen now measures its own width with a `LayoutBuilder` and gives that one number to the list and the bar. Two columns still start at 840 dp of content, the same test `_Checkout`'s `LayoutBuilder` makes; beside the rail that is a window of about 953 dp on iPad (872 + 81). Visible example changes: from an 840 dp window every list step gets the full 640 dp column, and a checkout whose content is under 840 dp shows the 640 dp column instead of a wider single column. Phones and windows under 840 dp are unchanged, and so are the committed portrait iPad mini captures (744 dp, no rail). Not changed here: the example app bar's title fit (#80) also measures the window, so beside the rail it overstates the room; and on a large phone in landscape the side safe-area insets offset the list and the bar differently, before and after this change.
- **D56 implementation note: a button's icon on its label's first line (#80).** `PaymentButton` with an `icon` lays out through `FirstLineRow`, which gains an internal `hug` mode: the text gets loose constraints and the row sizes to its content, so it works inside the button's centring, inside `IntrinsicWidth` and with an unbounded width. The label uses `TextWidthBasis.longestLine` when there is an icon, so a wrapped label hugs its longest line and icon and label stay one centred group, with the icon beside the first line. The gap is `related` (8 dp), as before. Icon size: medium and large buttons use `PaymentIconSize.medium`, the existing row-icon token, 20 dp at 1× and scaling with the text up to 1.6× (32 dp at 200%). That keeps the icon inside the 40 dp first line at 200%, so the button keeps its height and its 48 dp target, and it reads as part of the label rather than a 1× glyph beside two large lines. Small buttons keep 16 dp. Buttons without an icon keep the old `Row`. At 1× the geometry is unchanged (locked by a test); at 2× the icon is 12 dp wider, so `button_guard_test`'s 2× table moves the label 6 dp.
- **Example app bar title at 200% (#80).** The authorize step's title is the example's Material `AppBar` title, not a kit header, so the fix is in `flow_screen.dart`. `AppBar` caps its title at 1.34× text and lays it out on one line with an ellipsis, so at 200% on an iPhone SE "Konfirmasi pembayaran" became "Konfirmasi pe…". Wrapping was chosen over a shorter title, which would change the step's name only at large text. Breaks fall between words, as the D59a/P7a header rule asks: every step title is one or two words, and each word fits the room on a 375 pt phone. - **D53/D62 implementation note: side safe-area insets are applied once (#88).** In phone landscape (an iPhone 16 Pro reports about 59 dp each side; an Android cutout one side), the example's list and checkout bar used different content edges. No API change; the CHANGELOG has the migration. Example: the rail's `SafeArea` pads its start side only, and the body beside it removes that side's padding (`MediaQuery.removePadding`), so the flow screen sees only the inset on the far side. The flow screen subtracts the side insets it still sees from its `LayoutBuilder` width and passes that one width to `contentCap`, `listInset`, the checkout bar's cap and the title fit (#87). The #84 note's "not changed here" items are both fixed by this note and the next.
- **Example app bar title beside the rail (#87).** The #80 title fit measured `MediaQuery.sizeOf(context).width`, the window. From 840 dp the side rail takes part of the window, so beside it the fit overstated the room by the rail's width and its divider (81 dp on iPad, about 213 dp in the widget tests' font at 200%). The widget tests check it equals the width `NavigationToolbar` gives the title's paragraph, beside the rail at 1024 dp, at 484 dp without it, and in landscape with insets. In the test font at 200% "Konfirmasi pembayaran" is 478 dp. At a 1024 dp window it still fits the 627 dp beside the rail, so it keeps one line there, as #80's test already asserted. The wrap beside the rail shows in 840–875 dp windows (844 and 852 in the tests, an iPhone 16 Pro's landscape width), where `main` gave it one line and clipped it. ### Motion review (2 Nov 2026)

A read-only motion audit of the kit and the example at `main` 45b7ead, judged against native iOS and Android motion (D64). It found 15 problems (F1–F15). The orchestrator decided M1–M11 and the F7 rule, recorded here as D65–D76; later decisions from this work are D77–D80; the full wording is in the PRD decision table. Tracking issue #93; implementation issues #94–#106 in five phases (Phase 1 lands first, merges are serialized because of the changelog); M7b deferred to #107. The PRD marks behaviour that hasn't shipped yet as "(tracked in #N)".

- **D65 — reduced motion reads both platform flags (M1; F1; #94).** `PaymentMotion.reduced` is `MediaQuery.disableAnimations` or `PlatformDispatcher.accessibilityFeatures.reduceMotion`, and video autoplay also requires `accessibilityFeatures.autoPlayVideos`. iOS delivers Reduce Motion only as `reduceMotion` (engine `AccessibilityFeatures.swift`), so B9 did nothing on iPhone and iPad before this, and the B9 tests passed only because they inject the MediaQuery override. Reading `dart:ui` state is not a platform channel, so it stays within B11; no new API. Cost: a host can force reduced motion on but can't opt out of the OS setting, the safe direction.
- **D66 — reduced means zero, for both flags (M2; #94).** Every kit duration is 0 under either flag. Not chosen: Apple's short cross-fade under Reduce Motion, which would need two reduced modes and twice the tests. Proof is one helper, `expectStill` (nothing animating after one pump, in `test/helpers/reduced_motion.dart`), under three setups: the MediaQuery override, `FakeAccessibilityFeatures(reduceMotion: true)` and `FakeAccessibilityFeatures(disableAnimations: true)`.
- **D67 — SDK motion: gate where the API allows, name the rest (M3; F2; #100).** Bottom sheets, side sheets, wide confirm dialogs and toasts follow the tokens and reduced motion. Side sheets exit at `sheetExit` on the drawer curve (#99). Wide confirm dialogs and toasts enter at `enter` and leave at `exit` (#100). Toasts follow D77 (the newest wins) and D78 (a motion change clears the snack bar queue). Reduced motion shows the newest toast immediately. Replaced legacy controllers close with `hide`. Named SDK exceptions in PRD §3.7: Checkbox and Switch stroke and thumb, ink ripple and sparkle, the pressed-highlight fade, InputDecorator label float, Slider thumb, phone Drawer panel. Not chosen: kit-drawn replacements, a large rewrite of controls the kit deliberately reuses. Cost: B9 isn't absolute for those widgets; Android's "Remove animations" compresses them, iOS has nothing that does.
- **D68 — the drawer rule covers items, not the panel (M4).** "No motion for drawers" means drawer items and selection, as this file's motion table already said. The phone drawer panel keeps the platform slide and its edge-swipe gesture, as a native Android drawer does, and is a D67 exception. Not chosen: a kit side panel, which would lose the edge-swipe and rewrite tested focus handling.
- **D69 — full-width content swaps fade only (M5; F4; #95, #96).** Status content swaps with a fade at `enter` / `exit` and the height eased by `AnimatedSize` (`enter`, `easeInOut`), zero under reduced motion: the builder is `PaymentMotion.fullWidthSwap`, and the payment and verification status views use it. The explanation fades with the header, so the status reads as one change; in the payment view the amount between them stays put (D74). `fadeScale` is for compact elements only. Before #96 the status swap scaled the full-width `StatusBand` from 0.95, which moved each edge about 8.5 dp and slid the title, the reason full-width buttons don't scale on press; the tone and live region already carry the change.
- **D70 — `fadeRise` is a fixed 8 dp with a back mode (M6; F5; #95).** The builder slid 2 % of the child's height (about 13 dp on an SE, 25 dp on an iPad Pro for a full-screen step). It now rises a fixed 8 dp on every screen, matching the spec, and has a back mode (`back: true`) that fades only. Unreleased, so a changelog line is enough.
- **D71 — the example flow shows direction (M7a; F5, F14; #105).** Forward fades and rises 8 dp and back fades only. The outgoing step fades in place in either direction. A visited path identifies returns. Home and parent returns also fade when a scenario skips their earlier steps. A return removes the departed step from the path. Status to intro, identity or documents starts a new KYC pass and goes forward, whether or not the destination was visited. The departed status is removed even when the new pass starts at an unvisited step. `PopScope` stays and `flow_test` stays stable. Deferred, not dropped: hierarchical steps as `Navigator` routes so iOS edge-swipe and Android predictive back work (M7b, #107), a large coordinator change.
- **D72 — press feedback belongs to the host's theme (M8b; F9; #106).** The host's `ThemeData.splashFactory` owns the splash and the kit inherits it. The example sets `NoSplash` on iOS and keeps `InkSparkle` on Android. The Focus page documents it. Not chosen: the kit forcing `NoSplash` on iOS, which overrides the host theme across about 15 call sites. Cost: hosts that skip the docs keep ripples on iOS.
- **D73 — no kit haptic API (M9; F11, F15; #104).** Existing callbacks map to native haptics: press → Pay/Confirm `onPressed`; copy success → `onCopy`; selection → `onChanged`; success or error results come from the host. Charts expose an optional `onSelectionChanged` for scrub ticks, and the Focus page documents this mapping. Selection changes notify once per period, with null on return to rest; data-driven resets are silent. SDK `Feedback.forTap` and `forLongPress` (through `InkWell.enableFeedback` and the tooltip's long press) stay as SDK-owned behaviour, noted under B11. A feedback-event vocabulary can come later if hosts ask.
- **D74 — numbers don't animate (M10).** Amounts, balances, countdowns and totals change in place with tabular digits and never count or roll; the one allowed motion is the action-bar total's `quick` cross-fade after a re-quote. A payment amount must never show an intermediate wrong value. The cross-fade uses `easeOut` for both directions (#102). This records current behaviour.
- **D75 — no spring token (M11).** Sheets keep the curve tokens; the SDK bottom sheet already carries the release velocity into its fling and can be interrupted. No gain justifies re-implementing a tested sheet. This records current behaviour.
- **D76 — unknown upload progress under reduced motion shows the busy glyph (F7 rule, option 1; F7, F2; #97).** Both upload widgets show the static busy glyph beside "Uploading…", in the status badge, and no bar value, and known progress stays determinate. Before #97 the document slot's 50 % bar claimed progress the kit didn't know, and the capture field's indeterminate bar ignored reduced motion. Review fix (#97): the badge carries the upload label and the known percentage; the bar adds no semantics node. Unknown progress has no semantics value. Not chosen: an empty track, which still reads as "0 %".
- **D77 — the newest kit toast wins (#114).** Showing a kit toast replaces every showing or waiting kit toast. The current bar exits before the newest enters; reduced motion swaps instantly. Waiting replacements leave before their first visible frame. Replaced controllers ignore `update` and `dismiss`, complete `closed` when they leave, and legacy controllers close with `hide`. Owner decision, 2 Nov 2026. Waiting 4–10 seconds would report stale state; preserving the exit avoids a hard cut.
- **D78 — a motion change clears the snack bar queue (#117).** Before changing animation style, including the first kit toast replacing SDK timing, remove reachable bars with `hide`, clear the queue, then remove the current bar. This includes host bars: dropped waiting host bars never complete `closed`; dropped kit controllers complete `PaymentToastController.closed`. A dropped waiting legacy `showPaymentSnackBar` controller uses the SDK future, which never completes. Owner decision, 2 Nov 2026. The SDK disposes its shared animation on style changes, so a waiting bar freezes every later bar. Cost: hosts lose waiting bars when reduced motion changes.
- **D79 — touch scrubs return to rest on lift (#122).** On touch, a drag follows the finger, and the chart returns to rest when the finger lifts or the pointer is cancelled; `onSelectionChanged` reports `null`. A tap without a drag selects its period and keeps the label; a second tap on the same period clears it. A mouse is unchanged: hover selects, a click selects without clearing, and leaving returns to rest. Applies to line and bar charts; the sparkline keeps its tap toggle. Orchestrator decision delegated by the owner, 2 Nov 2026 (issue #122). Native charts (iOS Stocks and Health, Swift Charts `chartXSelection`) show a selection only while the finger scrubs. A phone has no hover, so a tap keeps its label until the next tap. D58's "leaving returns to rest" now covers the end of a touch scrub.
- **D80 — preserve host-themed close icons inside the toast pill (#127).** Third-review orchestrator decision for #125, 2 Nov 2026: disable the outer SDK close button and render its equivalent inside the pill after the action. Keep SDK color resolution, localized tooltip, 48 dp target, baseline geometry and legacy `dismiss` reason. Only content superseded before mount is blank; mounted content keeps painting through exit rebuilds. A square outer clip preserves the rounded inner pill corners. The SDK-identical themed close `IconButton` inside the pill is an exception to the PRD §12 raw-control grep (D80).

Motion Phase 4 package B (#103, #115) implements D66, D69 and D70: copy glyphs use a compact `quick` fade/scale; image loads keep the placeholder until the fade completes; reduced motion ends either swap immediately. `fadeRise` back mode keeps forward's wrapper structure with zero offset so a direction flip preserves leaving state. No new API or decision.
