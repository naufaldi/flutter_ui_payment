## The hard states are already designed

These cases cost money and support time. Each has a designed answer; [switch between them at the top](#states).

<Points>
  <Point title="The submit timed out after the server accepted it">
    The screen says “Don’t pay again.” A hatched band never looks like ordinary pending, and the one action is check status with the same attempt reference.
  </Point>
  <Point title="An older status arrives after a newer one">
    `PaymentAttempt.reconcile` rejects stale revisions, another attempt’s data, a mismatched server reference, and a success that turns into anything else without an official provider correction.
  </Point>
  <Point title="The total changed after the customer chose a method">
    `PaymentConfirmation` shows the old and new total and keeps confirm unreachable until the customer accepts.
  </Point>
  <Point title="The payment is still pending or unknown">
    No pay-again action. A new attempt appears only when the host allows it and the previous attempt is final and not a success.
  </Point>
</Points>

```dart
// Every status response goes through reconcile. Rejected snapshots leave the
// attempt as it was and tell you why.
final result = attempt.reconcile(snapshotFromYourAdapter);
if (!result.applied) debugPrint('ignored: ${result.rejection}');
attempt = result.attempt;

PaymentStatusView(
  attempt: attempt,
  amount: quote.total,
  onAction: (action) => host.handle(action), // only attempt.availableActions
);
```

## Your brand, light and dark

`PaymentTheme` is a `ThemeExtension`. Without it the kit follows your `ColorScheme`; with it you set colors, radius and amount style for light and dark. Same block, two looks, one package. [Theming](/concepts/theming/)

## Built to fit your app, not replace it

The kit never decides a price, a payment result or an identity check. Widgets render the data your backend passes and report what the customer did through callbacks. No network calls, no payment SDK, no router or state manager required.

<Responsibilities />

The full list, including input and consent, is on [Host-owned decisions](/concepts/host-owned/). Optional KYC capture, review and onboarding screens follow the same split: [KYC capture](/patterns/kyc-capture/).

**Accessibility is documented, not implied.** Status never relies on color alone, focus is visible, and the captured checkout and status screens reflow at 200% text with the key action still reachable. [Accessibility](/concepts/accessibility/)

## Questions

<Points variant="faq">
  <Question title="Does Rakit UI process payments?">
    No. It is UI only. Your backend and payment provider create, authorize and settle payments, and enforce idempotency. The kit displays the snapshots they return.
  </Question>
  <Question title="Which payment provider or backend does it need?">
    Any. You map your provider’s responses to the kit’s models, such as `PaymentAttempt` snapshots, in your own adapter. [Host-owned decisions](/concepts/host-owned/)
  </Question>
  <Question title="Which platforms are supported?">
    iOS (iPhone, iPad) and Android (phones, tablets). Flutter web is used only to preview the docs; desktop is out of scope. [Compatibility](/reference/compatibility/)
  </Question>
  <Question title="What does it cost?">
    Nothing. The package is MIT licensed and free to use in commercial apps. See the [licence](https://github.com/naufaldi/flutter_ui_payment/blob/main/LICENSE).
  </Question>
  <Question title="Is it ready for production?">
    It is an early 0.2.0 release with no known production users yet. Under Dart’s versioning convention, a 0.x minor release can include breaking changes. Review the code, test it with your backend, and [report what you find](https://github.com/naufaldi/flutter_ui_payment/issues/new).
  </Question>
</Points>
