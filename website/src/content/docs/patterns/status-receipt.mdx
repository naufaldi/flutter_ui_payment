## Usage

```dart
final va = attempt.snapshot?.instructions;

PaymentStatusView(
  attempt: attempt,
  amount: quote.total,
  busyAction: checking ? PaymentAction.checkStatus : null,
  instructions: va == null
      ? null
      : PaymentInstructions(
          instructions: va,
          clock: host.clock,
          onCopyNumber: copyToClipboard, // Future<bool> Function(String)
          onElapsed: refreshStatus,
        ),
  onAction: (action) => switch (action) {
    PaymentAction.checkStatus => refreshStatus(),
    PaymentAction.viewReceipt => openReceipt(),
    _ => host.handle(attempt.attemptId, action),
  },
);

RefundSection(refund: snapshot.refund, paidAmount: quote.total);

// A screen's body: the receipt scrolls and Done pins to the footer (D62).
PaymentFullPageView(
  title: 'Receipt',
  primaryAction: PaymentButton(label: 'Done', onPressed: finish),
  secondaryAction: PaymentButton(
    label: 'View details',
    variant: PaymentButtonVariant.quiet,
    onPressed: openDetail,
  ),
  child: PaymentReceipt(
    data: receiptData, // only for a payment your host confirmed as succeeded
    onShare: (share) => host.share(share.title, share.text), // Future<ShareOutcome>
    onCopyTransactionId: copyToClipboard,
  ),
);
```

The full sequence, including `PaymentAttempt` and `reconcile`, is in the [Quick start](/start/quick-start/#6-create-one-attempt-and-reconcile-snapshots).

## Behavior

- **Pinned action (D62).** Given a bounded height, for example as a `Scaffold` body, the status scrolls and the first action pins to a footer at the bottom. Under it goes one quiet action: your `secondaryAction` (such as "Done" once the attempt is final), otherwise "Contact support". The other actions stay in the content as hug buttons, after the instructions. Pass a banner, such as "Cancellation requested", as `header` so it scrolls with the status. Inside a scroll view every action follows the status as before.
- **Actions** come only from `attempt.availableActions`. While the outcome is unknown that is `checkStatus` alone. `startNewAttempt` appears only when your host allows it and the previous attempt is final and not a success.
- **Unknown** reads "Don't pay again." first, with a hatched band. The "last updated" row appears only once a host snapshot exists.
- **Instructions** sit after the explanation and before the actions, so the account to pay into comes before Check status. Above 1.5× text, when the actions are inline, they move after the actions; with a pinned footer they keep their place. They are not shown while the outcome is unknown, where an account to pay into would read as an invitation to pay again.
- **Countdown** uses the host clock and stops at zero; the widget only reports `onElapsed` and keeps the status check available. The virtual account number is set in the reference (monospace) font and steps fold under "How to pay".
- **Refunds** appear in `RefundSection`, beside the original payment, never instead of it. A refund above `paidAmount` is treated as invalid host data.
- **Receipt sharing** hands your callback only `ReceiptShareData`: merchant, transaction ID, time, total and the masked method. Line items and account identifiers are excluded. A failed or dismissed share never changes the receipt or the payment.

## Copyable host composition

The local example's `example/lib/compositions/host_payment_recovery.dart` combines the existing status and receipt patterns without `DemoCoordinator`. Copy it into the host alongside your product theme, such as `ProductLooks` in `host_checkout.dart`. It is example source, not an exported package API or an installed block system.

Pass the restored `PaymentAttempt`, amount and optional host-loaded receipt. `onAction(attemptId, action)` returns the host operation's future: a status check reconciles that same attempt, never submits a new payment. Rebuild with the updated attempt; use `Observation.unavailable` while retaining its last trusted snapshot when refresh fails. Persistence, reconciliation ordering, retries, networking and routing stay with the host.

Receipt rendering requires an accepted attempt with a succeeded host snapshot and a receipt whose `transactionId` matches `attempt.serverReference`. Early data, another transaction's receipt and an official correction away from success remain on the status view. The host must validate the full receipt payload; matching an identifier is only a presentation guard. While loading or retrying a receipt, pass `busyAction` and a safe notice through `header`; keep returning the callback future for local repeat protection. Share and copy callbacks use the existing allowlist and feedback behavior.

Try **Host payment recovery** in the gallery's **Status & receipt** section. Unknown offers a status check for the restored reference; the synthetic host returns a confirmed success fixture. Offline pending keeps the last known payment, and Receipt shows the confirmed result. These fixtures make no payment or platform call.
