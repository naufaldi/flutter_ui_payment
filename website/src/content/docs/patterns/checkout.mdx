## Usage

```dart
Scaffold(
  // In landscape the side insets go to the SafeArea, then the 16 dp gutter;
  // the action bar adds the same gutter to them, so the edges match.
  body: SafeArea(
    child: ListView(
      padding: const EdgeInsets.all(16),
      children: [
        const MerchantHeader(
          name: 'Ruang Bayar Akademi',
          category: 'Education',
          orderReference: 'RB-118',
          verified: true, // your verification flag
        ),
        const PaymentStepIndicator(
          steps: ['Verify', 'Checkout', 'Pay'],
          current: 1,
        ),
        PaymentSummary(quote: quote, previousQuote: previousQuote),
        PaymentMethodPicker(
          methods: methods,
          selectedId: selectedId,
          onChanged: (method) => requote(method.id),
        ),
        BalanceCard(
          state: host.balanceState, // sufficient, insufficient, unavailable
          balance: balance,
          shortfall: host.shortfall,
        ),
        PromoCodeInput(
          status: codeStatus, // idle, checking, applied, rejected
          onApply: host.applyCode, // Future<void> Function(String code)
          appliedCode: code,
          discount: discount,
          message: codeError,
          onRemove: host.removeCode,
        ),
      ],
    ),
  ),
  // The summary already shows the total, so the bar holds only the action.
  bottomNavigationBar: PaymentActionBar(
    action: PaymentButton(
      label: 'Review payment',
      busy: requoting,
      busyLabel: 'Updating total…',
      onPressed: requoting ? null : review,
    ),
  ),
);
```

Then the review and the host challenge, each as a screen's body. Given that bounded height, the content scrolls and the action pins to the bottom (D62):

```dart
Scaffold(
  appBar: AppBar(title: const Text('Review payment')),
  body: SafeArea(
    bottom: false, // the pinned footer pads the bottom inset itself
    child: PaymentConfirmation(
      header: sessionBanner, // optional: scrolls with the review
      quote: quote,
      method: selectedMethod,
      previousQuote: previousQuote, // after a re-quote: forces re-approval
      onConfirm: () => host.revalidateAndAuthorize(quote), // returns a Future
    ),
  ),
);

AuthorizationPrompt(
  header: totalSection, // the amount being authorized
  phase: authPhase,
  onStart: host.startChallenge,
  onBackToReview: backToReview,
);
```

Inside a `ListView` or `SingleChildScrollView` the height is unbounded, and the button follows the content as before. Pass a banner or summary as `header` rather than wrapping it and the widget in a `Column`, which would make the height unbounded.

## Behavior

- `PaymentSummary` leads with the total, then items, then every fee, discount and tax. Fees are never collapsed. With `previousQuote` it shows a notice with both totals.
- `PaymentMethodPicker` shows unavailable methods disabled with your `unavailableReason`. `PaymentMethodPicker.validSelection(methods, id)` returns `null` when a selected method disappeared or became unavailable, so you can clear it.
- `PaymentConfirmation` keeps `onConfirm` unreachable until the customer accepts a changed total.
- **Pinned action (D62).** With a bounded height, `PaymentConfirmation` pins pay and `AuthorizationPrompt` pins its confirm button, with the quiet "Back to review" under it, in a footer inside the bottom safe area: full width on phones, hug buttons at the end edge from 600 dp. An approved authorization has no footer. Hide your app's tab bar on these screens so the action is the only thing at the bottom. The example also hides it on pushed detail screens (D84); overview and history keep it, and the wide side rail is unchanged.
- After a re-quote, `PaymentSummary` shows a warning [banner](/components/banner/) that states old → new ("Was Rp102.500, now Rp104.000"). It has no close button while the payment is open (D48), so the only cue that the total changed cannot be hidden before paying.
- `AuthorizationPrompt` never receives a PIN, OTP or biometric result. Your SDK runs the challenge; you set the `AuthorizationPhase`. Canceled and failed have different copy, and neither is shown as a payment.
- `PaymentActionBar` pins the main action, with an optional total. On a phone in landscape it adds the side safe-area insets to its 16 dp gutters, the way a body in a `SafeArea` with 16 dp padding does, so the bar's content edges match the body's (#88). While `updating` is true it says "Updating total…"; disable the action yourself. When the summary above already shows the total, leave `total` out and show the update on the button (`busy` with a `busyLabel`), so the total isn't on the screen three times.
- For free-form amounts, such as a top-up, use [`PaymentCurrencyField`](/components/currency-field/).
- `BalanceCard` never compares the balance with the total, and `PromoCodeInput` never computes a discount. A discount reaches the price only as a new host quote with a `QuoteLineKind.discount` line.

## Connected host example

For a standalone runnable phone shell, inspected native screenshots and full
copyable source, use the [Checkout and Recovery block](/blocks/checkout-recovery/).
This pattern explains the domain contract; the block demonstrates its host layout.
For method availability, host-priced fees and re-approving a changed quote, see
the [Method choice and quote changes block](/blocks/method-quote/).

`example/lib/compositions/host_checkout_journey.dart` connects `InvoiceCheckout` from `host_checkout.dart` to `HostPaymentRecovery` from `host_payment_recovery.dart`. Copy those three source files into your host and adapt the callbacks. They use the Flutter SDK and this package, with no `DemoCoordinator`, router dependency or additional runtime layer. The screen expects bounded height, for example a `Scaffold.body`, so review, status and receipt keep their priority action pinned.

Try **Host checkout journey** in **Gallery → Checkout**. **Lost response** submits one synthetic attempt, shows an unknown outcome, then checks that same attempt and loads its matching receipt after a succeeded snapshot. **Pending then offline** first returns a pending snapshot; the first check fails and retains that snapshot, and the next check confirms success. Done resets this fixture. The scenario selector is developer tooling, not a customer recovery action.

The host passes a current quote already priced for the selected available method. Review blocks an expired quote, a mismatched/unavailable selection, or a balance method without a sufficient host verdict; the submit callback must still enforce price, eligibility and authorization on the authoritative side. This sample's wallet fixture requires no challenge. A host requiring one must finish it before exposing this send step, using the existing confirmation/authorization patterns; cancellation stays in that host step and must not be encoded as a null submit response. Changing terms after authorization requires host re-approval and re-authorization. Changing method must request a fresh quote in the host before allowing submission.

`newAttemptId` creates one identity before `onSubmit`. Persist it in the host before sending. A null response or transport exception preserves it as unknown; no automatic new attempt is created. `onCheckStatus` reconciles through `PaymentAttempt.reconcile`, ignoring wrong identities, changed references and stale revisions. It never submits. Return callback futures so the screen and kit controls retain repeat protection. Failed receipt loading stays on succeeded status with a safe message and View receipt retry.

`CheckoutOrder.merchantVerified` defaults to false. Set it only when the host has verified that merchant; otherwise the invoice and connected journey show no verified seal. Gallery fixtures opt in explicitly for their synthetic merchant.

`order.reference` identifies the host session. Replacing it invalidates outstanding callbacks, so a response from the previous order cannot populate the next one. The amount shown after submission comes from the submitted order, even when the host rebuilds with another quote. Do not use a quote refresh to change the order reference or clear an unresolved attempt. This example stores presentation state only while mounted: persistence, resume after process death, full receipt validation, credentials and platform sharing/clipboard implementations remain host responsibilities. Use the separate [recovery composition](/patterns/status-receipt/#copyable-host-composition) to render a restored host attempt.

## Pattern adoption

Changed-total approval uses `PaymentCheckbox`, aligned to the content gutter. Pay stays disabled until the customer accepts. Unavailable methods keep their reason below a muted label and show a thin disabled radio ring.

Promo code entry uses PaymentTextField with reference typography. Empty-code errors hide when editing starts.

## Filter foundation

Applied promo codes use an outlined chip and a separate 48 dp remove action.
