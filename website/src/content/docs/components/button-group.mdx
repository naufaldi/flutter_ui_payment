`PaymentButtonGroup` arranges related payment actions in a row or vertical stack. Use it for status actions, confirmations and module headers. Horizontal buttons hug their labels; the first action stays visible, and destructive actions occupy a separate final overflow group.

## Usage

```dart
// example/lib/screens/gallery_content.dart
PaymentButtonGroup(
              direction: Axis.vertical,
              children: [
                PaymentButton(label: 'Check status', onPressed: () {}),
                PaymentButton(
                  label: 'Start new payment',
                  variant: PaymentButtonVariant.secondary,
                  onPressed: () {},
                ),
              ],
            );
```

## In footers

`ViewFooter` stacks its group vertically at full width below 600 dp and at large text, primary on top. In page headers, groups only appear on wide screens; phones show a title-row link or ⋮ instead.

## Variants

Variants: horizontal auto overflow, horizontal none, vertical.

### Horizontal none

`collapse: PaymentButtonGroupCollapse.none` keeps one row of hug buttons while they fit. When they don't, every button stacks at full width, with the emphasized action (primary or destructive, passed last) on top. A stacked group never leaves a ragged edge (D45, #65).

### Horizontal auto overflow

The first action stays visible; trailing actions move into a ⋮ [menu](/components/menu/), and destructive actions always go there. On a phone that menu is a bottom action sheet.

### States and content

Choose horizontal overflow when supporting actions may move into a menu, no-collapse when all actions must remain visible, or vertical for a stacked group.

## Which variant when

| Situation | Variant / composition | Payment example |
| --- | --- | --- |
| Report footer | vertical | Stack Send before Cancel on phones; use automatic menu overflow for detail header actions. |

Use a single Button when there is one action.

## States

Each button keeps its own disabled and busy state. Overflow changes where an action appears, not when it is available.

## Do and don't

**Do**: Stack Send before Cancel on phones; use automatic menu overflow for detail header actions.

**Don't**: Place destructive and primary actions together in a vertical group.

## Content guidelines

Use action labels such as "View receipt" and "Contact support". Keep destructive actions separate from ordinary alternatives.

## Accessibility

Buttons keep their labels and keyboard behavior when moved into overflow. Long overflow labels wrap at large text.
