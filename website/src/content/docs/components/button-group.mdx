Related payment actions. Variants: horizontal auto overflow, horizontal none (stack on overflow), vertical. Nothing else exists. Use for payment status actions, confirmations and module headers. Horizontal buttons are normalized to hug width. The first action never collapses; destructive actions occupy a separate final overflow group.

## Usage

```dart
// example/lib/screens/gallery_content.dart
PaymentButtonGroup(
              direction: Axis.vertical,
              children: [
                PaymentButton(label: 'Check status', onPressed: () {}),
                PaymentButton(
                  label: 'Start new payment',
                  variant: PaymentButtonVariant.secondary,
                  onPressed: () {},
                ),
              ],
            );
```

## In footers

`ViewFooter` stacks its group vertically at full width below 600 dp and at large text, primary on top (D45, D59). In page headers, groups only appear on wide screens; phones show a title-row link or ⋮ instead (D59a).

## Variants

Variants: horizontal auto overflow, horizontal none, vertical. Nothing else exists.

### Horizontal none

`collapse: PaymentButtonGroupCollapse.none` keeps one row of hug buttons while they fit. When they don't, every button stacks at full width, with the emphasized action (primary or destructive, passed last) on top. A stacked group never leaves a ragged edge (D45, #65).

### Horizontal auto overflow

The first action stays visible; trailing actions move into a ⋮ [menu](/components/menu/), and destructive actions always go there. On a phone that menu is a bottom action sheet.

### States and content

The host supplies state and callbacks. Explain empty states and offer a next action. Use specific labels that wrap. Keep one primary action; separate destructive actions. Use semantic tokens and status text alongside visual marks.

## Which variant when

| Situation | Variant / composition | Payment example |
| --- | --- | --- |
| Report footer | vertical | Stack Send before Cancel on phones; use automatic menu overflow for detail header actions. |

Use a single Button when there is one action.

## States

Host state is explicit. Loading does not imply success; disabled actions retain a readable explanation. Interactive controls retain focus and pressed feedback.

## Do and don't

**Do**: Stack Send before Cancel on phones; use automatic menu overflow for detail header actions.

**Don't**: Place destructive and primary actions together in a vertical group.

## Content guidelines

Use sentence case and name the payment fact or action. Keep instructions visible and use semantic type, color and spacing tokens.

Stack Send before Cancel on phones; use automatic menu overflow for detail header actions.

## Accessibility

Labels wrap at large text. Controls retain their keyboard and screen-reader behavior. The host owns navigation and side effects.
