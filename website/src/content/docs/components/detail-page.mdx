Detail of a transaction, with header actions and host breadcrumbs. Do not nest in FullPageView: DetailPage owns its scroll. At 840 dp primary and secondary modules share space 2:1; narrower layouts stack primary before secondary. Narrow breadcrumbs show only the immediate parent, spoken as Back to that label. Pending preserves the structural header and replaces modules with skeletons.

## Usage

```dart
// example/lib/screens/gallery_views.dart
PaymentDetailPage(
        title: 'Rp102.500 to Toko Contoh',
        description: 'Paid with BCA virtual account · 1 Oct 2026',
        breadcrumbs: [
          PaymentBreadcrumb(label: 'Transactions', onPressed: () {}),
        ],
        actions: [
          button('View receipt'),
          button('Report a problem', variant: PaymentButtonVariant.quiet),
          button('Request refund', variant: PaymentButtonVariant.destructive),
        ],
        primary: [property(), attempts()],
        secondary: [
          PaymentDetailPagePropertyList(
            title: 'Merchant',
            pending: false,
            items: [
              const PaymentDetailProperty(
                label: 'Name',
                values: [PaymentDetailValue('Toko Contoh')],
              ),
              PaymentDetailProperty(
                label: 'Support',
                values: [
                  PaymentDetailValue.link(
                    PaymentLink(
                      label: 'Help centre',
                      external: true,
                      onPressed: () {},
                    ),
                  ),
                ],
              ),
            ],
          ),
        ],
      );
```

## Variants

Variants: primary, primary with secondary modules. Nothing else exists.

### States and content

The host supplies state and callbacks. Explain empty states and offer a next action. Use specific labels that wrap. Keep one primary action; separate destructive actions. Use semantic tokens and status text alongside visual marks.

## Which variant when

| Situation | Variant / composition | Payment example |
| --- | --- | --- |
| One transaction | primary with secondary modules | Payment and attempts are primary; merchant support is secondary. |

Use Overview page for a non-scrolling dashboard composition.

## States

Host state is explicit. Loading does not imply success; disabled actions retain a readable explanation. Interactive controls retain focus and pressed feedback.

## Do and don't

**Do**: Payment and attempts are primary; merchant support is secondary.

**Don't**: Nest DetailPage inside FullPageView.

## Content guidelines

Use sentence case and name the payment fact or action. Keep instructions visible and use semantic type, color and spacing tokens.

Payment and attempts are primary; merchant support is secondary.

## Accessibility

Labels wrap at large text. Controls retain their keyboard and screen-reader behavior. The host owns navigation and side effects.

Place page modules, detail property lists, detail tables or chart modules directly in primary and secondary. Do not wrap a titled module in another titled module.

Used in A02 and H04. Receipt and report actions are secondary; the payment, attempts and merchant modules have one heading each.
