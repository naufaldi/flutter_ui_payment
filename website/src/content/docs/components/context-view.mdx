Order context alongside a checkout. Views are bodies: the host supplies Scaffold and navigation. At most three header actions and one primary across visible actions; secondaryAction is not primary. Brand accepts only PaymentImage or PaymentIcon. externalLink must be external.

## Usage

```dart
// example/lib/screens/gallery_views.dart
PaymentContextView(
        title: 'Order context',
        description: 'Toko Contoh · Order DEMO-42',
        brand: const PaymentIcon(Icons.storefront_outlined),
        actions: [button('Copy order ID')],
        externalLink: PaymentLink(
          label: 'Merchant help',
          external: true,
          onPressed: () {},
        ),
        secondaryAction: button('Close'),
        primaryAction: button(
          'Continue to payment',
          variant: PaymentButtonVariant.primary,
        ),
        child: const PaymentPropertyList(items: facts),
      );
```

## Header and footer (D59a, D62)

- The brand icon centres on the title's first line, 12 dp from it.
- On phones one header action sits on the title row as "Label ›" and more go behind ⋮; nothing stacks under the title. Keep the task's own step in `primaryAction`.
- An ID such as the order ID is a reference row with a copy button (D57), not a separate "Copy order ID" button. Close and Cancel are quiet.
- At large text the header scrolls with the body, so the total and help link stay reachable on the first screen.

## Variants

Variants: context body with optional actions and footer. Nothing else exists.

### States and content

The host supplies state and callbacks. Explain empty states and offer a next action. Use specific labels that wrap. Keep one primary action; separate destructive actions. Use semantic tokens and status text alongside visual marks.

## Which variant when

| Situation | Variant / composition | Payment example |
| --- | --- | --- |
| Order beside checkout | context body | At 840 dp show supporting merchant/order facts beside payment. |

Use Full page view for the main page body.

## States

Host state is explicit. Loading does not imply success; disabled actions retain a readable explanation. Interactive controls retain focus and pressed feedback.

## Do and don't

**Do**: At 840 dp show supporting merchant/order facts beside payment.

**Don't**: Add a second primary Pay action to the context panel.

## Content guidelines

Use sentence case and name the payment fact or action. Keep instructions visible and use semantic type, color and spacing tokens.

At 840 dp show supporting merchant/order facts beside payment.

## Accessibility

Labels wrap at large text. Controls retain their keyboard and screen-reader behavior. The host owns navigation and side effects.

Header actions align to the content start. Phone footers stack full-width actions, primary first.

Used beside checkout at widths of at least 840 dp. The order context has supporting merchant help; the pinned checkout bar owns the primary Pay action.
