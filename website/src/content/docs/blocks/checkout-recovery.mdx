A single native phone journey: review the order and visible service fee, pay once,
recover a lost response, then read the matching confirmed receipt. Priority actions
stay pinned; content scrolls at large text. Amounts use the kit's numeric roles and
the layout follows the current host theme.

## Run the demo

From `example/`:

```sh
flutter run -d <device-id> -t lib/checkout_block_demo.dart
```

1. Review **Paket Belajar Rp100.000 + Biaya layanan Rp2.500** and pay the total.
2. The default **Respons hilang** scenario loses the response. No receipt appears.
3. Tap **Cek status**. The synthetic host confirms the same attempt; only then
   does its matching receipt appear. **Selesai** starts a fresh demo session.

The top bar is developer tooling: switch light/dark or choose **Skenario demo**.
**Pending lalu offline** returns pending, fails the first check and confirms on
the next check. **Struk gagal dimuat** confirms payment but fails the first receipt
load; **Lihat struk** retries without sending another payment. Selecting a scenario
deliberately resets the synthetic session; this is not a customer recovery action.
The demo uses a fixed clock; elapsed time never decides payment status. Sharing
returns dismissed and copying returns unavailable, without opening platform services.

## Composition and ownership

`HostCheckoutJourney` connects `InvoiceCheckout` and `HostPaymentRecovery`.
It accepts host data and async callbacks. Place it in a bounded body such as
`Scaffold.body` so the main action can stay pinned.

| Concern | Existing surface |
| --- | --- |
| Item, visible fee and method review | `PaymentSummary`, `PaymentMethodPicker`, `MerchantHeader` |
| One pinned action and large-text scroll | `PaymentFullPageView`, `PaymentButton` |
| Same-attempt recovery | `PaymentAttempt`, `PaymentStatusView`, `PaymentAction` |
| Confirmed receipt | `PaymentReceipt`, `PaymentReceiptData` |
| Shared look | `PaymentTheme`, scoped button/field themes, named host pay preset |

Read the [checkout contract](/patterns/checkout/#connected-host-example) for quote
expiry, method readiness, changed terms, authorization and session identity. Read
[status/recovery](/patterns/status-receipt/#copyable-host-composition) for restored
attempts and receipt gating. Those rules apply equally when you change this layout.

The real host must durably persist the attempt before sending, enforce server-side
idempotency and price/auth rules, parse provider responses, and validate receipts.
The example guards the receipt's transaction reference; that is not full backend
receipt validation. No elapsed delay establishes success or failure. Never turn a
status check or a missing response into a new submission.

## Verification and limits

Widget tests cover same-attempt recovery, offline checks without resubmission, receipt retry and a reachable action at 320 dp with 200% text. The host must persist attempts across process restarts. See [Compatibility](/reference/compatibility/) for device coverage.
