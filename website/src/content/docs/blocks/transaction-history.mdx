## Run and try

From `example/`:

```sh
flutter run -d <device-id> -t lib/history_block_demo.dart
```

Or open **Paged history** in the example Gallery. Scroll to **Muat lagi** (Load
more) to append a page. In the standalone demo, choose **Gagal memuat halaman
berikutnya** in the scenario menu to fail the next page once and try its retry.
Search **INV-2047** for the unknown outcome or **INV-2044** for a partial refund,
even before loading the page that contains it. The demo simulates a paged
server with fixtures; it makes no network request or financial operation.

## Assemble it in your host

Copy `merchant_history.dart`. Give it a bounded viewport and pass accumulated
records, the active query and filter, request state, and whether a next page is
available. The block uses one lazy scroll view and never receives a cursor.
Use `history_block_demo.dart` as the reference for the host side:

1. Apply the query and status filter at the server, before paging. Treat the
   cursor as opaque and scope it to the active query, filter and sort order.
2. On a query or filter change, clear the old rows and cursor and start a new
   request generation. Discard old successes and failures, even if cancellation
   is supported. Debounce text requests in the host if your service needs it.
3. Append rows and advance the cursor only after a successful next page. On
   failure, keep the rows and cursor and retry that same page. A null next
   cursor after success means there is no Load more action. Give each failure
   a distinct `error.attempt` with its display-safe `error.message`, even if
   an immediate retry fails with the same message.

The fixture uses stable, unique record IDs and a nonempty page whenever it
returns another cursor. Your data adapter should normalize overlapping or empty
intermediate pages if your service can return them. Authorize access on the
server and convert transport errors to display-safe copy in the host.

`MerchantHistoryDetail` composes `PaymentSheet`, `TransactionDetail` and a pinned
return button. The demo also supplies an `onReport` action that opens the
[Report a problem sheet](/blocks/report-a-problem/) for the selected transaction.
Omit the action for read-only inspection. Reporting never changes payment or
refund state. An unknown result never authorizes a new payment.

| UI | Existing library surface |
| --- | --- |
| Search, status filter and list states | `PaymentTextField.search`, `PaymentTabs`, `PaymentMenu`, `StateMessage` |
| Lazy rows and next-page action | `TransactionListItem`, `PaymentButton` |
| Status and facts | `TransactionDetail`, `StatusHeader`, `PaymentPropertyList` |
| Refund status | `RefundSection` |
| Detail layout | `PaymentSheet`, `PaymentSheetHeader`, `PaymentButton` |

Read the [history contract](/patterns/history/) and
[status/receipt contract](/patterns/status-receipt/). The pattern explains the
rules; this block demonstrates a host screen using them.

## Proof and limits

Widget tests cover paging, failed-page retry, stale replies, search, unknown
inspection, separate refunds and reachable controls at 320 dp with 200% text.
The Android example exercises the paging flow with the synthetic host, not a
live server. See [Compatibility](/reference/compatibility/) for device coverage.
