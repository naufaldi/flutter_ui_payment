## Run and try

From `example/`:

```sh
flutter run -d <device-id> -t lib/history_block_demo.dart
```

Search **INV-2047** for the unknown outcome, or **INV-2044** for a partial refund.
The status filters narrow the same host data. Search an absent reference to see
the no-match reset action. The developer menu selects loading, empty or failed
history; retry returns explicit synthetic data. The theme button switches looks.
No network, platform effect or financial operation occurs.

## Assemble it in your host

Copy `merchant_history.dart`. Supply already-filtered records, the current query,
filter, safe loading/error state and callbacks. The demo uses
`TransactionRecord.where` for five local scenarios; replace that with your own
retrieval strategy. For long histories, use lazy `TransactionListItem` rows and
host pagination instead of passing an unbounded list into this column-based kit
pattern. A server query needs host cancellation/stale-response protection.

`MerchantHistoryDetail` composes `PaymentSheet`, `TransactionDetail` and a pinned
return button for read-only inspection. Add a status-check
or receipt action when your host implements it; an unknown result never
authorizes a new payment. Copying or sharing is absent from this scenario.

| UI | Existing library surface |
| --- | --- |
| Search, filter and list states | `TransactionHistory` |
| Matching local records | `TransactionRecord.where` |
| Status and facts | `TransactionDetail`, `StatusHeader`, `PaymentPropertyList` |
| Refund status | `RefundSection` |
| Detail layout | `PaymentSheet`, `PaymentSheetHeader`, `PaymentButton` |

Read the [history contract](/patterns/history/) and
[status/receipt contract](/patterns/status-receipt/). The pattern explains the
rules; this block demonstrates a host screen using them.
